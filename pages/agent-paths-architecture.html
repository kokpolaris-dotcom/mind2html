AGENT 研发解耦 · 方向校准与解决方案

让团队回归价值：研发自持框架能力，底座专注垂类深水区

不是选错框架，而是两个团队的职责被低代码平台绑在了一起。

当前困境 精力错配，职责耦合
Agent 研发团队
只能在 Wanpix Admin 上开发
Wanpix Admin · 能力封装层
Mastra 的能力要逐个封装到 Admin
Mastra / Runtime 能力
  • 底座大量精力花在把 Mastra 能力开放给 Admin，只为让 Agent 团队能在 Admin 上开发 —— 并非高价值工作
  • 把 Wanpix Admin 做成「开发者能快速开发并交付业务」的平台，难度与投入远超预期；若仍走低代码路线，可参考 Coze / Dify 的复杂度与建设周期
  • 低代码平台与开发平台本是两个方向，硬要融合导致周期过长、非常别扭
核心价值 垂类 Agent 框架的壁垒在哪
  • 真正决定垂类 Agent 效果的，是面向该领域的上下文管理与记忆管理 —— 与 Coding Agent 同理
  • Coding Agent 好用不靠模型本身，靠对代码库的上下文管理（索引 / 检索 / 预算）与跨会话记忆
  • 垂类 Agent 同理：决定成败的是行业上下文与记忆的质量，而不是编排界面是否低代码
  • 因此底座应聚焦 记忆管理 · 上下文管理 · 文旅垂类知识库，这些是长期壁垒，应深度保护
解决方案 让团队回归价值
Agent 业务团队

基于完整的 Mastra 框架开发

自有仓库 · Git / IDE / Vibe Coding / CI，开发能力自持，不再等平台封装

底座团队

专注 Mastra 框架升级与垂类核心能力

fork 分支二次开发与版本升级维护；不再把框架能力逐个封装成 Admin 组件

方向一记忆管理

业务定规则 · 平台做机制三层记忆存储与租户隔离；文旅业务画像（旅行偏好 / 消费能力 / 同行结构）入长期记忆；TTL 与合规删除需同步清理向量、缓存与 Replay Fixture

方向二上下文管理

平台统一执行组装 / 窗口预算 / 截断 / 摘要全链路由平台执行，禁止各 Agent 自行拼接；每次模型调用记录 context.assembled

方向三文旅垂类知识库

平台做切片与召回商品 / SOP / 品牌 / POI 四类库差异化切片；结构化过滤 + 语义检索 + 关键词多路召回后统一重排

方向四实时态数据与时效裁决

正确性优先OTA 价格库存、票务余位、天气路况统一接入；冲突消解——知识库与实时接口不一致时由平台统一裁决，避免各 Agent 报价不一致

方向五行程编排与约束求解

文旅特有算法资产时间窗、地理距离、营业时间、预算、偏好构成约束模型；由求解器 + 可复用行程模板生成，不靠 Prompt 拼行程

方向六垂类评测体系

效果的度量基础行程合理性、报价准确性、退改签政策合规、拒答边界等场景评测集；支撑记忆 / 切片 / 上下文策略的效果回归

方向七基础能力提升

沙箱 + 交易治理沙箱增强：文旅业务工具的安全执行边界与配额；交易类操作治理：下单 / 改签 / 退款走幂等键、审批、审计与对账

解耦边界

Agent Contract · 统一接口与规范

接口稳定即可更换实现；自托管与平台托管同一入口，研发能力不再绑定平台排期

低代码平台与开发平台分离，各自演进；不要求 Agent 研发只能通过 Admin 开发。

演进路径
01 存量原地增强 · 保留 Wanpix + Mastra，补 Trace / Replay / CI·CD / 灰度回滚
02 增量团队自托管 · 新增 Agent 自主开发并自托管，经统一 Gateway 接入门户
03 下一代 Runtime · 共性瓶颈被真实业务证明后，由 Runtime/Core 统一立项
