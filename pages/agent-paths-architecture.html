AGENT 研发解耦 · 方向校准与解决方案

让团队回归价值：研发自持框架能力，底座专注垂类深水区

不是选错框架，而是两个团队的职责被低代码平台绑在了一起。

当前困境 精力错配，职责耦合
Agent 研发团队
只能在 Wanpix Admin 上开发
Wanpix Admin · 能力封装层
Mastra 的能力要逐个封装到 Admin
Mastra / Runtime 能力
  • 底座大量精力花在把 Mastra 能力开放给 Admin，只为让 Agent 团队能在 Admin 上开发 —— 并非高价值工作
  • 把 Wanpix Admin 做成「开发者能快速开发并交付业务」的平台，难度与投入远超预期；若仍走低代码路线，可参考 Coze / Dify 的复杂度与建设周期
  • 低代码平台与开发平台本是两个方向，硬要融合导致周期过长、非常别扭
核心价值 垂类 Agent 框架的壁垒在哪
  • 真正决定垂类 Agent 效果的，是面向该领域的上下文管理与记忆管理 —— 与 Coding Agent 同理
  • Coding Agent 好用不靠模型本身，靠对代码库的上下文管理（索引 / 检索 / 预算）与跨会话记忆
  • 垂类 Agent 同理：决定成败的是行业上下文与记忆的质量，而不是编排界面是否低代码
  • 因此底座应聚焦 记忆管理 · 上下文管理 · 文旅垂类知识库，这些是长期壁垒，应深度保护
解决方案 让团队回归价值
Agent 业务团队

基于完整的 Mastra 框架开发

自有仓库 · Git / IDE / Vibe Coding / CI，开发能力自持，不再等平台封装

底座团队

专注 Mastra 框架升级与垂类核心能力

fork 分支二次开发与版本升级维护；不再把框架能力逐个封装成 Admin 组件

方向一 记忆管理 业务定规则 · 平台做机制

三层存储Run 内工作记忆 / 跨会话用户记忆 / 长期知识记忆，各自独立的准入、TTL 与权限
读写一致性统一 Memory API；写入幂等、跨实例一致；Checkpoint 只存快照版本 + 读取引用 + 待写幂等键
召回策略向量 + 关键词混合召回、时间衰减、冲突消解、注入 token 预算，全链路可解释
遗忘与删除TTL 到期、用户删除、合规擦除；向量、缓存、备份与 Replay Fixture 同步清理
与业务界线「记什么 / 何时读 / 何时忘」由业务团队定规则，平台提供并强制执行上面这套机制

方向二 文旅垂类知识库 平台做切片与召回

商品库按 SKU / 类目 / 属性切片；价格与库存独立成块，便于时效更新而不重建全库
SOP 库按流程步骤 + 角色切片，一条流程不切碎，保证步骤完整召回与顺序正确
品牌库按调性 / 话术规范 / 禁忌切片，召回后作为生成语气约束而非事实来源
POI 库按地理层级切片，支持「附近 / 同城 / 线路」三类检索与行程串联
多路召回结构化过滤 + 语义检索 + 关键词并行召回，按知识库类型分别设权重后统一重排
效用保障切片语义边界由业务确认；召回率与命中准确率进评测集，badcase 反哺切片与召回策略
解耦边界

Agent Contract · 统一接口与规范

接口稳定即可更换实现；自托管与平台托管同一入口，研发能力不再绑定平台排期

低代码平台与开发平台分离，各自演进；不要求 Agent 研发只能通过 Admin 开发。
